# 六选五 PWA 性能/工程遗留项收益分级评估（2026-11-20）

- **日期**：2026-11-20
- **评估人**：技术架构（柯桥良）
- **范围**：C1–C7 七项性能遗留项 + BACKLOG「刻意不修」技术项（B-L2/L3/L4、fitLongNames）
- **性质**：**评估档**。只出收益判定与理由，不改生产代码、不提交、不发布、不重跑实测。
- **证据基线**：直接采用 `docs/perf-review-2026-11-20.md`（架构双盲静态+动态）与 `docs/qa-perf-baseline-2026-11-20.md`（QA 独立复算）已实测数据，本轮**不重复测**。

## 判据（用户口径，原文）

> 收益大 = 玩家可感知，或有实测数据支撑的显著量化改善，且风险可控。
> 收益小 = 纯理论/微秒级/无实测支撑/影响面极小 → 从文档删除。
> 已有实测证伪的担忧（如 C4 大列表 0.6ms）应判「收益小→删」，不要因「技术上可以优化」就判大。

## 证据口径声明

- 「**已实测**」仅指两份报告中已跑出的数值；「**静态推断**」指从源码/渲染模型推导、未经真机验证。两者严格分开，不互相替代。
- 本地实测环境为 **headless Edge + 本地静态服务（无 gzip、无网关延迟）**，是**最乐观条件**；真机弱网、真机帧率均**未实测**。凡涉及这两者的收益，一律按「无实测支撑」处理。
- 已上线项不纳入评估：P1-2 版本自检改 `/version.json`（温启 92,586B→318B）、P1-4 版本 bump 门禁（见 `docs/perf-p1-fix-log-2026-11-20.md`）。

## 前提假设（假设变则结论重估）

1. 目标平台以**现代浏览器 PWA** 为主（SW/cache-first、BroadcastChannel 已是依赖前提），老内核为长尾。
2. 无「首屏慢 / 等待态卡顿」的玩家投诉或线上工单证据。
3. 首访成本的主要痛点是弱网/中低端机场景——但该场景本轮**无真机实测**，仅本地乐观数据。

## 1. 结论速览（C1–C7）

| 编号 | 遗留项 | 判定 | 核心证据（已实测 / 静态） | 一句话理由 |
|---|---|---|---|---|
| **C1** | 首屏脚本+DCL 前全执行 | **收益大 → 做** | 已实测：gzip 520,738 B；4×CPU 温启 DCL 178ms、按钮绑定 156.9ms | 唯一有硬体积数据支撑的结构性首屏项，弱网/中低端可感知 |
| C2 | 等待态 box-shadow 无限重绘 | 收益小 → 删 | 静态：style.css:1291/1947；**未测真机帧率** | 纯静态推断零实测，视觉改动风险中 |
| C3 | 500ms localStorage 常驻轮询 | 收益小 → 删 | 静态+QA：roomStore.js:149，只读 touch 键、不发网络 | 微秒级、对首屏无影响、已有事件兜底 |
| C4 | 大列表无虚拟化 | 收益小 → 删 | 已实测：200 行 0.6ms，无任何卡顿 | 担忧被实测证伪，用户点名判小 |
| C5 | 登录页 blur(46px) | 收益小 → 删 | 静态：style.css:4427，非动画一次性栅格化 | 影响面仅限登录首帧一次，需美术重做 |
| C6 | .card-wrap 常驻 will-change | 收益小 → 删 | 静态：style.css:1800，一屏 6–8 张牌 | 报告自评收益/代价平衡、无内存压力实测 |
| **C7** | 首访请求翻倍（裸路径+版本化） | **收益大 → 做** | 已实测：冷启 70 笔 /js\|css = 35 裸 + 35 版本化；首访传输 1.88MB | 首访传输近翻倍，收益被实测钉死，改动局部可控 |

**汇总**：收益大→做 = **C1、C7**（2 项）；收益小→删 = C2、C3、C4、C5、C6（5 项）。

## 2. C1–C7 逐条详评

### C1 · 首屏 31 个 defer 脚本 + 4 份样式 DCL 前全执行 —— **收益大 → 做**

> 对应 review 报告 P1-1。报告实测口径为 index.html 引用 **32 个脚本 + 3 份样式**（任务卡写 31/4 为近似），此处以实测报告为准。

- **证据（已实测）**：
  - 首屏引用资源 **1,373,745 B 原始 / 520,738 B gzip**；index.html 自身 92,286 B / 32,289 B gzip（`perf-review §1`）。
  - 首访脚本传输 799,614 B（31 个）；首访总传输 1,880,185 B。
  - 4×CPU 温启动 DCL **178 ms**、`#btn-create` 绑定 156.9 ms；温启动脚本传输 0 B（全命中缓存）。
  - 静态识别的非首屏模块候选：recordsView.js 99,709 B、settleView.js 70,596 B、seatSheetView.js 65,736 B、achievements.js 44,391 B，合计约 280 KB 原始。
- **证据（静态）**：`index.html:1326-1376` 32 条 defer；`sw.js:139-142` 记录「game.js 同步 IIFE，任一模块 404 整页白屏」。
- **理由**：七项中**唯一有硬体积数据支撑的结构性优化**。温启动脚本已由 SW 缓存归零，脚本体积成本集中在首访与版本 bump 后首次；弱网/中低端机下 520KB gzip 全量解析执行会显著劣化 DCL，玩家可感知。符合「有实测数据支撑的显著量化改善 + 风险可控」。
- **若做的改动面与风险**：
  - 改动面：按「启动必需 / 进房才需要 / 战绩与后台才需要」三档拆加载，用受控延迟 `<script>` 注入并保持 `?v=` 一致；同步调整 `sw.js` PRECACHE 清单。
  - 风险 **中**：全局 IIFE 的加载顺序/竞态（`Ach.accumulate()` 结算调用、`recordsView.create()` 启动依赖，`perf-review §4` 待实测项4）；拆错模块会整页白屏（`sw.js:139-142` 有明证）。
  - **前置条件（风险可控的前提）**：拆分边界必须先由主程序验证，**不得按文件名猜**；拆前拆后各跑一次 `node scripts/probe-perf-once.js` 对拍（主程序在实施阶段验证）。未过此验证前不得动手。

### C2 · 等待态 box-shadow 无限重绘 —— **收益小 → 删**

- **证据（静态）**：`style.css:1291` `.st-thinking .opp-avatar` 的 `seatWait` 2s infinite 动画扩散 box-shadow 0→4px；`:1947` `.pulse-dot` 的 `pulse` 1.2s infinite 扩散到 14px；`game.js:2086` 确认等待提交时插入 `.pulse-dot`。
- **证据（实测边界）**：本轮 rAF 采样**只覆盖首页与规则弹窗（16.7ms/60fps），未覆盖「等待其他玩家提交」状态**；QA 三态实测也不含此状态。**零实测支撑**。
- **理由**：纯静态推断——「box-shadow 是 paint 属性、理论上每帧重绘」成立，但**是否真的掉帧/耗电从未测过**。用户口径明确「无实测支撑 → 收益小」。且改动为视觉重做（伪元素光晕 transform/opacity），需美术对齐、probe-motion + 真机各复验一遍，风险中，不满足「风险可控」。
- **若做的改动面与风险（供重开参考）**：改独立伪元素 + transform/opacity，保留 `prefers-reduced-motion` 兜底（probe-motion.js:245-261 已有断言）。风险中：光晕边缘与 overflow 裁切可能变化。
- **删的处置**：从待办文档删除，正式承认不修。**重开条件**：若 QA 在阶段5 真机等待态实测确认掉帧/掉电（perf-review §4 待实测项2），再重新立案。

### C3 · 500ms localStorage 常驻轮询 —— **收益小 → 删**

- **证据（静态+QA 实测）**：`roomStore.js:149-158` 模块初始化即 `setInterval(..., 500)`，无条件读 `LS_TOUCH` 并解析；QA 2.2 确认它**只读 localStorage touch 键、不发网络请求，不构成网络风暴**。另有 BroadcastChannel（:118-133）与 storage 事件（:135-146）两条通知路径。
- **理由**：每秒 2 次读取+JSON 解析一个极小对象是**微秒级固定成本**，报告自评「量级小……对首屏无影响，故列 P2」。命中「微秒级 + 影响面极小」。且改动要保留旧内核/跨标签兜底，有回归风险（probe-multi-tab.js 需复验）。
- **若做的改动面与风险**：仅本地演示模式且有活跃房间时启动轮询，进房开启、离房清除。风险低-中：跨标签兜底不能丢。
- **删的处置**：从待办文档删除，承认不修。

### C4 · 大列表无虚拟化（content-visibility 零文件）—— **收益小 → 删**（用户点名）

- **证据（已实测，担忧被证伪）**：QA 2.3 真浏览器注入合成记录、MutationObserver 后量真实 DOM：10 行 0 ms / 50 行 0.2 ms / **200 行 0.6 ms**，三点全低于 16.7ms 单帧；负向断言「清空后残留 0 行」成立。`records.js:63` LIMIT=200 写入即裁剪。
- **理由**：review 报告原本静态推断「低端机一次渲染可能落在 100ms 量级」，**被 QA 实测证伪（0.6ms）**。用户口径点名此类判小。逐行 listener 随 innerHTML='' 一起丢弃，未发现泄漏；seatSheetView 表情 13+8、飞行节点上限 6，不构成长列表风险。
- **删的处置**：从待办文档删除，承认不修。不做分页/虚拟化/`content-visibility`。

### C5 · 登录页 blur(46px) —— **收益小 → 删**

- **证据（静态）**：`style.css:4427` `filter: blur(46px)` 作用于 520/600px 两块；`index.html:256-257` 首屏存在但**非动画**。报告 P2-3 自评「静态模糊只付一次栅格化成本……优先级低于 P1」。
- **理由**：一次性光栅化、非持续动画；影响面仅限登录页冷启动首帧一次，微秒/毫秒级、无实测劣化数据。命中「影响面极小 + 无实测支撑」。改动需美术重做视觉（预模糊图/radial-gradient），得不偿失。
- **删的处置**：从待办文档删除，承认不修。

### C6 · .card-wrap 常驻 will-change —— **收益小 → 删**

- **证据（静态）**：`style.css:1798-1801` `.card-wrap` 常驻 `will-change: transform`，配合 transition；一屏 6–8 张牌。报告 P2-4 自评「本场景牌数少，收益/代价接近平衡，**不建议立即大改**」。
- **理由**：常驻图层提升在 6–8 张牌量级下无内存压力实测证据，报告作者本人判定不建议改。命中「影响面极小 + 无实测支撑」。改动还需复测拖拽跟手度。
- **删的处置**：从待办文档删除，承认不修。

### C7 · 首访请求翻倍（35 裸路径 PRECACHE + 35 版本化路径）—— **收益大 → 做**

- **证据（已实测）**：QA 2.1 冷启服务器侧收到 **70 笔 /js\|css = 35 裸路径 PRECACHE + 35 带 `?v=` 版本化路径**；QA D2 独立列为建议项。与首访传输 1.88MB（脚本 799,614 B）吻合。版本 bump 时同样触发 35 脚本全量重下（QA 2.1 C 行）。
- **证据（静态，机制已核实）**：`sw.js:100-201` PRECACHE 写裸路径，`withShare()`（:92-95）只拼 sharecode、不拼 `?v=`；`index.html` 引用带 `?v=`；两者是不同 cache key，首次版本化请求必然 miss。`matchSameVersion()`（:309-319）的**取舍①**（:300-301「缓存条目没有 v 视为可用」，专为裸路径 PRECACHE 设计）是此机制的关键约束。
- **理由**：七项中第二条**有硬实测数据支撑的显著量化改善**——消除首访约一倍脚本下载（约 799KB 未压缩 / gzip 约 250KB 量级），弱网/流量计费场景玩家可感知。改动面局部（PRECACHE 写入时拼当前 app-version，使首次 install 写入带 v 的 key 与 HTML 引用精确对齐），且已有 QA 双盲工具（`tools/qa/perf-sw-cache.js`，4/4 自验）+ 已上线的 P1-4 版本 bump 门禁可复验 → **风险可控**。
- **若做的改动面与风险**：
  - 改动面：`sw.js` PRECACHE 键统一到带 `?v=`；同步核对 `matchSameVersion` 取舍①（改为带 v 后该分支不再命中，需确认离线兜底与换 sharecode 场景仍成立）。
  - 风险 **中**：改动触及「防混版本」防线——该防线有真实线上事故背景（`sw.js:294-303` 小王事件：旧 JS 被复用致玩家以为规则没区分大小王）。绝不能为省流量放宽版本校验。
  - **前置条件**：改动后必须跑 `node tools/qa/perf-sw-cache.js` 复验「版本 bump 全量重下 + 同版本 0 请求 + 离线兜底」三态，并由 QA 确认 sharecode key 一致性（QA D2 明确要求评估 matchSameVersion 兼容）。

## 3. 刻意不修技术项 · 做/删建议

| 项 | 现象 | 判定 | 理由 |
|---|---|---|---|
| B-L2 | 9 处 `justify-content: space-*` 老内核间距为 0 | **删** | 仅老内核 + 观感、仍可读可用；无法用 margin 等价表达（改了会把第二个元素往里推、布局错位，比不修更糟） |
| B-L3 | 3 处 `flex-wrap` 老内核换行后行首多间距 | **删** | 老内核+换行双条件同时满足概率很低；负 margin 方案会覆盖容器自身 margin，风险大于「行首偏 6px」 |
| B-L4 | 兼容层不预缓存，老内核离线没间距 | **删** | 仅老内核离线；收录了也命中不了（PRECACHE 键带 sharecode、兼容层 URL 带 `?v=`，非同一键）；要修得给 network-first 加 ignoreSearch + 统一 URL |
| fitLongNames | layout thrashing | **删** | 已判亚毫秒、刻意不修（任务卡给定）；微秒级 + 无实测劣化 |

四项均为 watch（刻意接受、只观察不排期）状态，影响面全部落在「老内核 / 离线 / 亚毫秒」极小范围，且各自修复方案的风险 ≥ 收益。**统一判「删」= 从待办文档移除、正式承认不修**。

**重估条件**：若产品要求明确支持老内核且用户占比显著（假设1 变化），B-L2/L3/L4 需重新评估；在此之前维持删除。

## 4. 「收益大 → 做」清单（供制作人裁定）

| 优先级 | 项 | 为什么做 | 前置验证（风险可控的前提） |
|---|---|---|---|
| 1（先做） | **C7** 首访请求翻倍 | 收益被实测钉死（70→35 笔、首访传输近翻倍）；改动局部；有 QA 工具 + 门禁可复验 | QA 跑 `perf-sw-cache.js` 复验三态；确认不破坏 matchSameVersion 混版本防线 |
| 2（后做） | **C1** 首屏脚本折叠 | 唯一结构性首屏优化（gzip 520KB）；弱网/中低端可感知 | 主程序先验证拆分边界（Ach.accumulate / recordsView.create 依赖）；拆前后 `probe-perf-once.js` 对拍 |

- **最值得做的一项**：**C7**。理由——收益被 QA 双盲实测直接钉死（不是估算），改动面最小且局限在 sw.js 一处，已有工具链与门禁兜住风险；C1 收益更大但风险更高，须排在 C7 之后、且通过前置验证才动手。
- **最大风险**：**C1 拆分破坏同步 IIFE 依赖链 → 整页白屏**（`sw.js:139-142` 明确「任一模块 404 整页白屏」）。这是七项中唯一可能造成线上阻断的后果，必须用前置验证兜住，不得按文件名猜拆分边界。
